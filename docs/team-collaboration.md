# 天亨 SKYDOME 双人协作约定

更新日期：2026-11-18。状态：**可讨论的协商初稿**；功能分配、优先级和期限尚未得到双方及老板确认。本文准备协作方式，不表示新功能已经实现。

## 共同目标与角色

两位共同负责人共同交付一个能在本机启动、操作、验证和解释的校园安全 Demo。每人完整负责一个小功能的页面、接口、数据处理、测试与说明，再由另一人检查；不按“一个人协调、另一个人开发”或固定前后端拆分。

| 共同负责人 | 首轮暂定交付 | 互相检查与演示 |
|---|---|---|
| `heqiucan` | A：已完成执行任务的追加式补充记录；利用对现有链路的熟悉程度负责该功能的完整实现 | 检查 B 的接口、搜索与错误恢复；串联现有主线及 A 的演示 |
| `houda-codes` | B：知识中心按类别与关键词联合检索，并修复页面与接口搜索口径不一致 | 检查 A 的持久化、任务隔离及原报告不变；演示 B，并参与主线联调 |

这是责任分配建议，不代表上下级关系。双方可以交换模块；一人遇到阻塞时共同调整范围，不能把未完成工作默认为另一人的责任。仓库写权限不代表产品决策权或管理权；交接记录已确认 `houda-codes` 有 write 权限，本轮不修改仓库权限。

逐项输入、输出、文件范围、验收与暂定估时见 [首轮迭代计划](iteration-01.md)。

## 分支与交付路径

- `main`：通过互审、验证后合入的共同基线。
- `codex/team-collaboration`：本轮协作计划和准备材料；不作为两人长期混写功能的分支。
- `codex/task-follow-up-notes`：建议用于 A，由 `heqiucan` 开发。
- `codex/knowledge-category-search`：建议用于 B，由 `houda-codes` 开发。

本轮仅在准备分支提交并推送文档。后续由双方在 GitHub 发起准备文档及各自功能的 PR，另一人审查后合入 `main`。这些 PR 尚未创建，本轮不自动创建 Issue/PR、发消息或改权限。互审是协作约定，不表示已配置分支保护或强制审批规则。

同事阅读准备材料（在自己的 checkout 中，先确认没有未提交改动）：

```powershell
git status --short --branch
git fetch origin
# 首次本地没有该分支时执行；已有时使用 git switch codex/team-collaboration。
git switch --track origin/codex/team-collaboration
```

正式开始 A 或 B 时从当时的最新 `main` 建立自己的功能分支。准备文档未合入时也可先在 GitHub 阅读，不需要把另一个人的功能提交带进自己的分支：

```powershell
git status --short --branch
git switch main
git pull --ff-only origin main
# 以下二选一，不连续执行；建议分支已存在时直接切换，不重复创建。
git switch -c codex/task-follow-up-notes
# git switch -c codex/knowledge-category-search
```

提交、推送、验证命令见 [CONTRIBUTING.md](../CONTRIBUTING.md)。一个 PR 对应一个能验收的功能。PR 中写明页面变化、接口兼容性、实际测试结果和仍未实现的边界，包含可复现的操作步骤。

合并前先同步远端基线；需要带入 `main` 更新时，在干净的功能分支执行 `git fetch origin` 和 `git merge origin/main`，解决冲突后重新验证。不要用强制推送掩盖冲突，不覆盖对方尚未提交的修改。

同一台机器上的多个对话如果共享同一 checkout，也共享当前分支与文件。交接对话只交接，本对话负责准备；以后并行开发应各用自己的 clone 或明确隔离的工作区。仅新建对话不会隔离 Git 分支。

## 文件边界与接口变化

| 范围 | 首轮安排 |
|---|---|
| A 独立文件 | 新增补充记录服务、类型、面板及对应测试；只在 `ExecutionTaskDetail.vue` 接入；A 负责新增数据库表 |
| B 独立文件 | 新增知识服务/路由、`KnowledgeCenter.vue`、请求状态逻辑及对应测试；B 负责知识页从 `App.vue` 的局部抽取 |
| `backend/app/main.py` | 唯一预期同时涉及的主要接线文件。A 增加 notes 路由注册；B 移出原知识路由并注册新路由。各自保持小差异，后合入者解决接线冲突并请另一人复核 |
| `backend/app/database.py` | 首轮由 A 增加独立表和约束。B 沿用既有知识表与类别字段，无数据库迁移 |
| `frontend/src/App.vue` | 首轮由 B 负责知识页接线。A 默认仅修改任务详情，不增加全局状态；主线演示不等于重构 App |
| `api.ts`、`schemas.py`、全局 CSS、锁定文件、启动脚本 | 优先沿用，新增类型/样式放各自模块；若必须改共享文件，先在计划或后续 PR 中写明影响，再同步另一人 |
| `docs/api.md`、`docs/database.md` 等共用文档 | 各功能先写独立说明与验收记录；合并时仅增补对应小节，避免整页格式化 |

新接口契约以 [iteration-01.md](iteration-01.md) 的草案为起点。开始编码前，两人核对路径、字段、长度限制、排序、幂等和错误码，记录协商结果；尚未确认的字段不能直接宣传为现有 API。既有接口保持路径与响应兼容，新增可选参数不得破坏旧调用。

共享文件需要超出约定范围修改时，提出“要改哪里、为什么、影响哪个接口/测试”，由双方协商。契约变化需同时更新类型、调用方、相关测试和说明，不在任一方分支悄悄改变已约定的语义。

## 互审与完成标准

1. 每人先按自己的验收表交付前后端、测试、操作说明及真实结果；未执行项标为未验证。
2. 另一人在独立临时数据库或自己的 Demo 数据上操作，检查成功、无结果/失败、刷新和数据边界，避免只看截图。
3. A、B 可独立合入；先完成哪项就先审哪项。两项合入后共同走一次现有主线，再分别演示新增行为。
4. 提交前运行既有 Python 回归、前端 Node 测试及构建；不要用 `/health` 替代业务验收。纯文档更正通常只需差异、链接和内容检查。
5. 不重置旧事件或执行记录。新表初始化需要兼容已有数据库；不得删除旧库来掩盖迁移问题。

联调缺陷由改动引入方先定位，另一人协助复现；无法明确归属时共同判断。每次同步只需说明已完成的可验证行为、当前阻塞、下一步及影响对方的接口变化，不设单方面指派关系。

## 首先向老板对齐

以下话术可直接复制，由两人共同确认后发送；本轮未代发：

> 我们准备共同负责下一轮 Demo，各自交付一个包含前后端和测试的小功能，再互相检查。当前已有“事件—规则核查—模拟执行—结果反馈”链路，模型自主规划、真实设备和正式审批还没有接入。下一轮您最希望验证哪个业务目标？下次演示面向谁、希望现场看到哪条操作链路，验收标准是什么？演示的具体日期、时间和时区，以及可投入的工作时间能否先确定？我们的初步建议是“任务结果补充记录”和“知识分类检索”，等目标对齐后再共同确定范围与排期。

需要记录的结果：首要使用者/问题、必须展示的行为、明确不包含的范围、验收人、演示时间与时区、双方可投入时间。如果期待真实模型或真实设备，先另行评估接入条件与成本；不能把它们默认为这两个小功能的附带交付。

## 数据与运行约定

沿用 [.gitignore](../.gitignore)。公开仓库只提交必要源码与说明；密钥、运行数据库、日志、个人绝对路径及含人员信息的第三方参考图不进入提交。两台电脑各用自己的 SQLite 数据，不经 Git 或 OneDrive 共享运行数据库。新增测试使用临时库和虚构文本。

本轮不变更 `.runtime/share`、Cloudflare 分享进程、部署方式、系统权限或模型配置。临时分享地址依赖原电脑运行，不是部署流水线；同事开发按本地启动文档执行。
